## Problem Statement

起点是一句抱怨：「我想要做个全平台的代理软件，就像 FlClash 一样，但是他的 UI 我不喜欢。」

追问之后，这句话展开成四个具体的痛点，而且作者本人四条全中：

1. **桌面端体验差** —— 窗口、托盘、快捷键、右键菜单没有接住桌面系统的习气，用起来像把手机 App 塞进模拟器。
2. **信息架构乱** —— 连接、代理、规则、日志、配置、订阅堆在一起，改一个设置要翻三层。
3. **视觉不好看** —— 配色、字号、间距、动效是 Material 默认味的堆砌，没有自己的气质。
4. **配置/分流难用** —— 改节点、改规则、改策略组、导入订阅门槛高，容易点错。

四条同时成立，意味着这**不是一个换皮问题，而是要做一个新客户端**。

目标不是商业产品，是**开源 + 自用**：成功标准是「自己每天愿意打开它」，以及差评里不出现「又一个换皮 FlClash」。

## What Makes This Cool

**把看不见的路由变成看得见、讲得清的东西。**

代理客户端最让人困惑的不是「连不上」，而是「它到底把我的流量送到哪儿去了」。现有客户端只告诉你当前选了哪个节点，不告诉你某个域名为什么走了这条路。

**必须诚实的一点**：mihomo 的 `/connections` 已经返回 `metadata`、`rule`、`rulePayload`、`chains`，metacubexd 这类面板也已经把它们渲染出来。**所以这不是独有数据，是表现力问题。** 差异点在于把这条链路做成可读、可键盘操作、能和主界面联动的桌面原生视图，而不是一个网页表格。

Aether 的核心视图是一条**路由透视（X-Ray）**：

```
进程 → 域名 → 命中规则 → 策略组 → 节点 → 流量 / 存活时长
```

初稿里这一行的最后一项写的是「结果（延迟/失败）」。经源码核实，`/connections` 的每条记录里**没有任何**表示延迟或成败的字段——延迟只存在于 `/proxies/{name}/delay`，那是节点的属性；拨号失败的连接根本不会留在列表里。所以这一项换成了真实存在的数据。详见「API 契约（已核实）」。

分期交付，**不要把它当成一个整体承诺**：

| 能力 | 里程碑 | 说明 |
|---|---|---|
| 实时连接的路由透视（含规则链、搜索/筛选、键盘导航） | **M1** | 只对已经发生的连接生效，数据现成 |
| 域名路由预演（HUD） | **M2** | **需要绕路实现，见下文** |
| 一键把观察到的路由固化成显式规则 | **M5** | 依赖配置模型稳定后再做 |

**为什么域名预演要推迟到 M2**：mihomo **没有**「给定域名，返回匹配规则」的接口。`/connections` 只对已存在的连接返回规则信息。所以「输入域名立刻预演路径」不能直接实现，必须从下面三条里选一条：

- **(a) 真实探针**：通过 mihomo 发一个真实请求，再从 `/connections` 里读回这条记录。便宜、诚实，但有两个缺陷：探针来自 Aether 自己的进程，所以 `PROCESS-NAME` 类规则评估的是 Aether 而非目标应用；而且它有副作用（真的发出了请求）。

  探针必须**可关联**，否则读不回来——一个快速完成的 HTTP 请求可能在两次轮询之间就消失了：

  - **关联键用（host, destinationPort）组合**：`/connections` 的 metadata 里有 host 和端口，没有 URL 路径。所以用一个固定可解析的主机（如 `example.com`）+ 一个随机高位端口（30000-60000）作为唯一键。**不要用 `.invalid` 或随机子域名**——前者不解析，后者无法在 metadata 里区分（只有 host 没有 path）。
  - 探针期间把 `/connections` 的 WS 推送间隔从 500ms 提到 **100-200ms**，只在预演窗口内提高频率。
  - 已核实：拨号失败只产生 `/logs` 的 WARN 行，**不保证**会出现在 `/connections` 快照里（连接关闭后会立即从 manager 中删除）。所以预演必须打到一个**能成功建立连接**的慢速端点上；若只能打关闭端口，该方案不成立，改用项目自有域名的泛解析子域 + 活的慢速端点（需先注册域名），或退回到「只搜索现有连接」。
  - 3 秒内未观测到记录 → UI 显示「未能观测到该连接」，**不猜、不伪造结论**。
- **(b) 本地规则引擎**：在客户端重实现 mihomo 的匹配语义（DOMAIN / GEOSITE / GEOIP / RULE-SET / PROCESS-NAME / 逻辑规则 / provider 加载 / 优先级），并用差分测试对拍。昂贵，但离线且无副作用。
- **(c) 只做搜索**：不做预演，HUD 退化为「搜索当前连接」。这其实等于把 M1 的列表搬到一个浮层里。

**本设计选 (a)**，并接受它的两个缺陷，在 UI 上明确标注「以 Aether 进程身份预演，进程相关规则可能不适用」。如果 M2 实测发现预演结果与真实请求偏差过大，再升级到 (b)。

## Constraints

- 单人开发，日常主要语言是 Java，UI 栈从零开始。**技术选型不以此为依据**（见 D14），但排期必须计入学习成本。
- 目标平台：Windows / macOS / Linux / Android。**iOS 不做**（开源 Clash 系客户端进不了 App Store）。
- **Windows / macOS / Linux 的界面渲染必须一致**——这是硬约束，指渲染结果，不指功能。
- 主战场是 Windows（开发机为 Windows 10，工作目录 D:\a-proxy）。
- 第一版只做系统代理，不做 TUN（由一日实测决定是否放在 M2 起点，见 Open Questions）。
- 设计是主要差异点。功能对齐到「能自用」即可，不追新特性。
- 开源，GitHub Releases 分发。v1 不做自动更新、不做 macOS 签名公证。

## Premises

1. **不自研代理内核**，直接用 mihomo v1.19.32，通过其 Clash 兼容 REST API 驱动。
2. **两套壳、一套设计系统**。桌面与移动共享 design tokens 和交互规范，页面布局各自实现。
3. **不做 iOS**。
4. **桌面先行，Windows 优先**。平台相关能力藏在 `PlatformProxy` 接口后，但**这不等于 macOS 是低成本移植**（见 Feasibility 说明）。
5. **差异点是设计纪律**，不是功能数量。
6. **第一版只做系统代理**，TUN 是后续里程碑——但在写第一行 UI 代码之前，先跑一天实测决定。
7. **开源 + GitHub Releases**，v1 无自动更新；**macOS 不签名不公证是已接受的风险**（见 README 的已知问题），不是待决问题。
8. **三端渲染一致** —— 因此排除所有「借系统 WebView」的方案（Tauri / Wails / Neutralino）。
9. **技术栈：Electron 45 + React 19 + TypeScript（桌面）/ Kotlin + Jetpack Compose（Android，M4）**，共享一份 `tokens.json`。

### 渲染一致 ≠ 功能一致

审查发现这两件事在 v1 里被混为一谈。明确区分：

- **渲染一致**（发布门槛）：同一份前端代码在三个系统上布局、颜色、字体渲染一致。靠 Electron 自带 Chromium 保证。
- **功能一致**（按平台分别交付）：系统代理、TUN 依赖各平台原生实现，**不共享代码**。

因此：**Windows 先有功能，macOS / Linux 先只有界面。** 见 Milestones 与 Distribution Plan。

## Cross-Model Perspective

Codex 冷读（未看过对话过程）的原文要点：

1. **最酷的版本**：把主窗口做成「网络飞行记录仪」，每条连接展示 `process -> destination -> matched rule -> proxy group -> node -> result`，再配一个 Raycast 式全局 HUD；点一条走错的路可以直接预览规则改动并固定节点。
2. **最能说明你在乎什么的引文**：`现代化桌面控制台, 移动优先的极简体验, 两端共用设计规范，但不强行共用同一套页面布局`。它指出这不是「把 FlClash 做好看」，而是把设计系统和页面布局刻意分开。
3. **已有项目给你的 50%**：`clash-verge-rev/clash-verge-rev` 提供 Tauri 壳、Rust 侧 mihomo 生命周期、Clash API 集成、系统代理、服务模式、配置管理、托盘管线；剩下的 50% 才是产品。（本项目选 Electron，故只借鉴模块划分，不复用其代码。）
4. **它认为错的前提**：「第一版只做系统代理，不做 TUN」。验收方法：开系统代理跑一个正常工作日，用 `Get-NetTCPConnection` 对比 mihomo `/connections`，测十个日常应用。若 3 个以上绕过，或非浏览器流量中超过约 30% 绕过，则 TUN 应进 v1。
5. **周末会先做什么**：一个真正的垂直切片，而不是假数据看板。

**判决与修订**：采纳 1 的分期版本、2 的洞察、4 的验收方法、5 的原则。**3 和 5 的技术栈建议不采纳**（D12/D14/D15）。**Codex 没有发现第 1 条的实现障碍**——它把「输入域名预演路由」当成可行功能，而 mihomo 并没有这个 API；该缺陷由 D16 修正。

## API 契约（已核实）

来源：mihomo 源码 `3f27ef3`（2026-10-21，branch Meta）与 Meta-Docs `2a6ba6b`（2026-10-22）。这一节推翻或修正了初稿里的两处假设，**实现前以此为准**。

| # | 事实 | 对设计的影响 |
|---|---|---|
| F1 | `/connections` 的连接对象只有 9 个字段：`id` / `metadata` / `upload` / `download` / `start` / `chains` / `providerChains` / `rule` / `rulePayload`。**没有** latency、status、error、closed、duration | 结果列改为「流量 + 存活时长」 |
| F2 | `chains[0]` 是**实际拨号的出站**，最后一位才是最外层策略组。示例：`["HK","Auto","Proxy"]` | **初稿写反了**。UI 必须反转后显示为 `Proxy ▸ Auto ▸ HK` |
| F3 | `GET /connections?interval=ms` 的 WebSocket 按间隔推送**完整快照**（不是增量），也支持 HTTP chunked | 采集用 WS，不自建定时器；连接多时单条消息较大 |
| F4 | 只有成功拨号才记 INFO 日志（带规则与链路）；失败只记 WARN。日志 payload 语法**没有版本化契约** | 失败只做全局计数，不逐条并入列表 |
| F5 | 没有「给定域名返回匹配规则」的接口；`GET /rules` 只有规则列表和累计命中计数 | 域名预演只能靠真实探针 |
| F6 | `find-process-mode` 取值 `always` / `strict` / `off`，默认 `strict`（仅在进程规则被求值时查询） | 必须注入 `always`，否则进程列为空 |
| F7 | `/connections` 里的 `memory` 来自缓存，只有调用过 `/memory` 才刷新 | 不要用它做内存监控 |

**兼容性原则**：Clash API 没有正式版本化规范，字段是逐步加的（`providerChains`、`memory`、`sniffHost` 都是后加的）。客户端必须容忍未知字段和字段缺失，不能假设固定 schema。

## Config 模型

这是审查指出的最可能返工处，必须先在纸上定死。

**三层文件，各司其职：**

```
<userData>/profiles/<id>/upstream.yaml   # 订阅/导入的原始配置，只读，从不改写
<userData>/overrides.yaml                # 用户规则与覆盖项，由 Aether 自己生成
<userData>/profiles/<id>/runtime.yaml    # 每次启动时合并生成，交给 mihomo
```

- **runtime.yaml 必须与 upstream.yaml 同目录。** 上游配置里的 `proxy-providers` / `rule-providers` 常用相对路径，换个目录就失去基准。若将来必须换位置，得先把所有 provider 路径重写为绝对路径，并用一份带 provider 的订阅做回归。

- **upstream.yaml** 永不修改，因此其中的注释和字段原样保留。
- **overrides.yaml** 只由 Aether 写入（结构化的 `rules.prepend`、`rules.append`、`proxies`、`proxy-groups`），不假设用户手写注释。

**合并语义（必须显式，不能靠「用户优先」一句话带过）：**

| 顶层键 | 策略 | 说明 |
|---|---|---|
| `rules` | prepend / append | 显式插入，不替换上游规则 |
| `proxies` / `proxy-groups` / `proxy-providers` / `rule-providers` | 按 `name` 的 map 合并 | 同名整条替换，新名字追加 |
| `dns` | **deep-merge，Aether 侧优先** | `nameserver-policy` 按 key 合并；`enable` 不得被 Aether 单方面关闭 |
| `sniffer` | deep-merge | |
| `profile` | deep-merge | `store-selected` / `store-fake-ip` 由 Aether 固定值 |
| `tun` | `enable` 强制 `false`，其余透传 | 导入配置可能自带 `tun: {enable: true}`，会让内核申请驱动和权限，违反 v1 的无 TUN 约束；同时清空 `redir-port` / `tproxy-port` |
| `mixed-port` / `external-controller` / `secret` / `find-process-mode` | Aether 注入，覆盖上游 | |
| 其它顶层键与未知字段 | 透传，上游优先 | 记录到启动日志，便于排查兼容性问题 |

**为什么必须逐键定义**：初稿只定义了顶层合并，而真实机场订阅普遍带 `dns`、`sniffer`、`proxy-providers`、`rule-providers`，以及 `use` + `filter` 形式的策略组。这些结构一旦合并错，表现是"节点在、但分流不对"或"某个组是空的"，排查成本极高。

**合并后必须做的两件事**：

1. 重新校验：`mihomo -t -f runtime.yaml`（用同一个 `-d` home）。
2. 检查引用完整性：`proxy-groups` 里引用的节点名、`use` 引用的 provider 在合并后是否都存在。缺失时给出可读错误，而不是让内核静默起一个空组。

**回归样本**：至少要有一份带 `dns` + `proxy-providers` + `use`/`filter` 策略组的真实订阅结构（脱敏），作为合并逻辑的固定测试输入。

同名节点替换而不是追加，是为了让「改一个节点」不会在列表里留下两条同名项；如果将来需要保留多份，用显式改名，别改合并规则。
- **runtime.yaml** 每次启动按 `upstream → 注入端口/密钥 → overrides` 顺序合并生成；其中 `mixed-port`、`external-controller`、`secret`、`find-process-mode` 由 Aether 注入，**覆盖** upstream 中的同名配置。

**合并与生效规则：**

1. 写文件用「临时文件 + 原子 rename」，不原地改。
2. 应用前先跑 `mihomo -t -f runtime.yaml` 校验，失败则保留上一份 good 配置并给出可读错误。
3. 通过 `PUT /configs?force=true` 热重载；失败则回滚到上一份。
4. 订阅刷新只替换 `upstream.yaml`，不触碰 `overrides.yaml`。
5. `find-process-mode: always` —— 否则进程列默认是空的（mihomo 默认 `strict`，只在规则需要时才解析）。代价是每次连接有一次进程查找开销；在 UI 上提供关闭开关。

## PlatformProxy 接口

```ts
export interface ProxyState {
  enabled: boolean
  server?: string          // "127.0.0.1:7890"
  bypass?: string[]
  autoConfigUrl?: string   // PAC 脚本地址，必须快照与还原
  autoDetect?: boolean     // WPAD 自动检测，必须快照与还原
  owner: 'aether' | 'external' | 'unknown'
}

export interface PlatformProxy {
  readonly platform: 'win32' | 'darwin' | 'linux'
  isSupported(): boolean
  getSystemProxy(): Promise<ProxyState>
  setSystemProxy(opts: { server: string; bypass?: string[] }): Promise<void>
  clearSystemProxy(): Promise<void>
  needsPrivilege(): boolean          // Windows(HKCU) = false
}

// 主进程侧（与平台无关）
class ProxyOwnership {
  snapshotBeforeApply(state: ProxyState): Promise<void>   // 落盘原状态 + owner=aether
  restoreOnStartupIfStale(): Promise<'none' | 'restored' | 'conflict'>
  restoreOnExit(): Promise<void>
  markCleanExit(): Promise<void>
}
```

- **M1 只实现 Windows**。macOS 的实现（SystemConfiguration / 授权）与 Linux（环境变量 / GSettings）各自独立，代码零复用。
- **PAC / WPAD 必须一并处理**：启用 Aether 代理时删除 `AutoConfigURL` 并把 `AutoDetect` 置 0，否则自动配置会盖过手动代理；还原时按快照写回。只改 `ProxyEnable` / `ProxyServer` 是不完整的实现。
- **原生层**：Rust + napi-rs 插件，直接写 `HKCU\...\Internet Settings` 的 `ProxyEnable` / `ProxyServer` / `ProxyOverride` 并调用 `InternetSetOptionW` 广播变更。写在用户态，**不需要管理员权限**。
- 不选 PowerShell / `reg.exe` 的原因：无法可靠广播配置变更，接受新设置的进程不确定。

## 崩溃恢复与残留代理

这是这一品类最危险的事故：应用崩溃后系统代理仍指向一个已死的端口，用户整台机器断网。

- 应用代理**之前**，把完整的原状态（`enabled` / `server` / `bypass` / **`autoConfigUrl`** / **`autoDetect`**）和一个 `owner: aether` 标记写入 `<userData>/proxy-state.json`，并记录 pid 与时间戳。**PAC 字段必须进快照**——只存 enabled/server/bypass 会导致还原时静默丢掉自动配置。
- 正常退出：还原代理 → 删除标记文件。
- **启动时**：若标记文件存在且不是本进程写的，判定为上次异常退出，自动还原并提示「已恢复上次的系统代理设置」。
- 若标记存在但当前系统代理已被别的程序改过（`getSystemProxy` 与快照不符），**不要覆盖**，只提示并清除标记。
- 孤儿内核：`proxy-state.json` 同时记录 mihomo 的 pid、`external-controller` 端口和**当次的 secret**。启动时若端口被占用，先用旧 secret 请求 `/version`：
  - 返回 200 → 这是上次遗留的内核，复用或提示用户终止；
  - 返回 401/404 → 是别的程序，另选端口启动，不干扰；
  - 连接被拒或超时 → 无法判定，同样另选端口。
  **不能用配置哈希做二次判定**：mihomo 的 `/version` 不返回哈希。旧 secret 本身是 128 位随机值，能通过 Bearer 校验就已经证明所有权。超时也会落到"无法判定"，所以**不要把它当成"端口空闲"**。
- 关机 / 注销：监听 `powerMonitor` 的 `shutdown` 与 `before-quit`，尽力还原代理。即使来不及，自启 + 启动时检测残留是第二道防线。
- 卸载：README 明确要求先退出应用；安装器提供「清理残留代理」入口。
- **测试**：CI 里用 `taskkill /F` 模拟强杀，验证下次启动能自动还原。

## Approaches Considered

### Approach A: 分叉 Rebrand
Fork 现有客户端，剥 UI 重写。
- Effort: S / Risk: Med
- 优点：管线白拿，一周能用。
- 缺点：要在别人的抽象里重写全部界面；对外像换皮；且主流桌面客户端是 Tauri/Flutter，与本项目的三端一致约束冲突。

### Approach B: 自建 Electron + React（选中）
- Effort: M / Risk: Low-Med（对一个首次使用 Electron 的人，按 1.5-2 倍时间估）
- 优点：代码全是自己的，信息架构完全可控；三端渲染一致；组件生态适配目标审美。
- 缺点：系统代理、进程守护、打包自行实现；移动端无共享代码。

### Approach C: Electron UI + Rust 守护进程
Mullvad 同款。
- Effort: L / Risk: Med
- 优点：UI 与网络逻辑彻底解耦，TUN 与提权服务自然落位。
- 缺点：v1 多 2-3 周，调试链路变长。

### Approach D: X-Ray 先行
只做只读路由透视器，附着在现成 mihomo 上。
- Effort: S / Risk: Low
- 优点：一周出可截图的东西，零管线风险。
- 缺点：不是完整客户端；有停在观察器的风险。

### 被否决的技术栈
- **Tauri 2**：系统 WebView 导致三端渲染不一致。
- **Flutter**：桌面嵌入层最不成熟，且与被抱怨的 FlClash 同引擎。
- **Compose Multiplatform**：其核心优势是共享 UI 代码，而本项目明确不共享页面布局。
- **JavaFX**：UI 生态弱，做不出目标审美。

## Recommended Approach

**Approach B：自建 Electron + React，Windows 先行，M1 交付一个能日常上网的垂直切片。**

### 版本与架构矩阵（锁死）

### 模块与关键约束

```
桌面
  renderer/    React + TS，自建 tokens + Radix + cmdk + TanStack Virtual
  main/        mihomo sidecar 生命周期 / 配置合并 / 代理所有权 / IPC
  native/      Rust + napi-rs（Windows 系统代理）
  core-link/   与 mihomo 的 REST 客户端；只跑在主进程，secret 不下发渲染进程
移动（M4）
  Kotlin + Compose + VpnService + mihomo(gomobile AAR)
共享
  tokens.json  （M1 只管桌面；生成的 Compose Theme 在 M4 再做）
```

- controller 绑定 `127.0.0.1`，随机 secret 由主进程持有；渲染进程**从不**直接访问。
- **端口动态分配**：启动时用 `net.createServer({port:0})` 取下空闲端口，注入 `mixed-port` 与 `external-controller`，避免与其它客户端抢占 7890/9090。端口冲突检测失败时给出明确错误，不静默。
- **窗口生命周期**：主窗口隐藏即 `destroy()`；HUD 窗口（M2）首次唤起时创建，隐藏后保留 60 秒再销毁，不做预热。因此 M1 的「托盘常驻内存」目标**不包含 HUD**。
- **内核重启策略**：10 分钟内最多重启 3 次，退避 1s / 2s / 4s；超过后进入「内核不可用」状态并显示可操作的错误，不再自动重启。用户主动退出后不重启。
- **内核启动契约**：`mihomo -d <profiles/<id>> -f <profiles/<id>/runtime.yaml`。地理库（`Country.mmdb` / `geosite.dat`）由打包资源目录复制或链接到该 `-d` home 下；`mihomo -t` 校验时必须使用**同一个 `-d`**，否则校验结果和实际运行不是一回事。
- **地理库**：随包分发 `Country.mmdb` 与 `geosite.dat`（SHA-256 锁定），缺失或校验失败时给出明确错误状态，不静默使用空库。
- **打包**：mihomo 放 `extraResources`（天然在 ASAR 之外，**不需要也不应该**再加 `asarUnpack`）；开发态与打包态用 `app.isPackaged` 分支解析路径（打包后走 `process.resourcesPath`）；CI 中对 macOS/Linux 产物 `chmod +x`（Windows checkout 会丢可执行位）；macOS 签名跳过时在 README 说明 `xattr -d com.apple.quarantine`。

## Milestones

**v1 = M1.5**（第一个可分发的版本；M1 是可以自己跑起来用、但不对外分发的内部里程碑）。以下「M1/M1.5/M2/…」是唯一的里程碑语言。

### M1 —— Windows 垂直切片（可日常自用）
包含：脚手架、mihomo sidecar、**配置导入（本地 YAML，或从 URL 拉取一次；不做订阅刷新）**、配置合并与校验、节点切换、系统代理开关、代理所有权与崩溃恢复、**开机自启**、原生托盘菜单、**X-Ray 主视图（严格按「UI 规范（M1）」：左栏节点树 + 连接列表 + 行内详情；采集用 `/connections?interval=500` 的 WS 快照 + 60 秒环形缓冲）**、命令面板（节点 + 六个动作，不做域名预演）、最小日志环形缓冲（错误面板 + 拨号失败计数）、退出清理。

## Acceptance Criteria

**测量协议（不满足则为未通过）**

- 硬件：开发机（Windows 10 Home）实测并在 README 记录型号；同一台机器上比较。
- 内存：统计 `Aether.exe` 全部进程 + `mihomo.exe` 的 Working Set 之和；启动后预热 5 分钟；每 30 秒采样，取 10 次中位数。
  - 托盘态（主窗口已销毁、无 HUD、无连接页打开）：< 150 MB（放宽自 100MB，因为含 mihomo 进程）。
  - 开窗态（主窗口打开 30 秒后）：< 450 MB。
- 冷启动：从进程创建到托盘图标出现，5 次取中位数，< 1.5 s（只衡量「有反应」）。
- **代理就绪**：从进程创建到配置校验完成、`/version` 握手成功、系统代理已应用，5 次取中位数，< 4 s。这条才是「能用」，必须单独衡量，不能被托盘图标出现的时间掩盖。
- 节点切换：从 IPC 调用到 UI 乐观更新 < 50 ms；到 `/proxies` 回读确认 < 1000 ms（留出两个 500ms 的 WS 快照周期作为余量）。
- 长稳：预热 30 分钟后，每 5 分钟采样 8 小时；最后一小时中位数不得超过第一小时中位数的 110%。
- 渲染一致：同一窗口尺寸（1280×800）、DPR=2、使用内置字体、排除系统窗口边框。**比较方式为「遮罩文字后比较布局几何与 token 颜色」，不是整图像素 diff**——三个平台的字形光栅化（DirectWrite / CoreText / FreeType）必然不同，要求整图像素一致是不现实的目标。最终阈值由 M2 的 spike 实测后校准，不预先拍板。

**设计验收（M1）**

- **密度**：1280×800 主视图下，不滚动可见连接行 ≥ 18；域名列至少完整显示 24 个字符。
- **键盘完成率**：六个核心任务（切节点、开关代理、筛选连接、展开详情、重启内核、退出）100% 可仅用键盘完成。
- **tokens 纯度**：组件代码中不允许出现裸色值、裸 px、裸字号，由 lint 规则强制，违例即失败。
- **三端布局同构**：同一视口下三平台的布局几何与 token 颜色一致（M2 起验证，方法见上一条）。

**M1 功能验收**

- 导入一份本地 Clash YAML（仅 YAML 文本或文件，不支持 URL/base64），能上网。
- 切换节点生效，连接列表的 `chains` 随之改变。
- 开启系统代理后，访问受控 URL 的出口 IP 发生变化；关闭后复原。
- 正常退出后：mihomo 进程不存在、系统代理已还原 —— 由本地脚本自动验证（M1.5 接入 CI 后，CI 跑同一脚本）。
- `taskkill /F` 强杀后重启：自动还原系统代理并提示。
- 重启验证：注销/重启后自启生效，系统代理指向一个可用端口；禁用自启后重启，手动启动 Aether 能检测到残留代理并还原。
- 键盘可完成：开关代理、切节点、唤起命令面板、在连接列表中移动与筛选。

**M2 交付前必须通过**：域名预演的准确率对拍（20 个域名，与真实请求的匹配规则一致率 ≥ 90%，进程相关规则除外并显式标注）。

## 错误状态清单（每一条都要有 UI 行为）

| 状态 | 触发 | 要求的行为 |
|---|---|---|
| 无配置 | 首次启动 | 引导导入，不自动启动内核 |
| 配置非法 | `mihomo -t` 失败 | 展示 stderr 的可读摘要，保留上一份 good 配置 |
| 订阅过期 / 不可达 | M4 起 | 使用缓存副本并标注「已于 X 过期」 |
| 内核不可达 | REST 握手失败 | 重试 + 退避；超过阈值进入错误态 |
| 内核反复崩溃 | 10 分钟内 3 次 | 停止重启，展示日志入口与「手动重启」 |
| 端口冲突 | 动态分配失败 | 明确报错并建议关闭其它客户端 |
| 全局快捷键被占用 | 注册失败 | 提示并允许重新绑定 |
| 系统代理被他人修改 | 启动时快照不符 | 不覆盖，提示并清除标记 |
| 地理库缺失/损坏 | 校验失败 | 明确报错，提示重新下载或重装 |
| 权限不足（mac/Linux 未来） | 需要提权 | 说明原因并提供授权入口 |
| 配置写入失败 | 磁盘写满 / 权限不足 | **不得应用代理**；保留上一份 good 配置并报错 |

## Open Questions

1. **TUN 是否进 M2 起点** —— 由一日实测决定。若 TUN 提前到 M2，Windows 需要 Wintun 驱动 + 管理员权限；macOS 需要带授权的 helper，这与「不签名不公证」直接冲突，届时必须重新评估 macOS 的功能范围。**这是唯一会改变平台计划的变量。**
2. **macOS 的系统代理实现方式** —— SystemConfiguration 反复授权还是 helper。M3 开工前必须定。
3. **Android 内核集成可行性** —— `mihomo` 没有官方维护的 gomobile AAR，需要自建 Go mobile 包装并跟随内核升级。M4 前先做 spike，不通过就重新考虑（例如自建 TUN 转发层）。
4. **设计系统载体** —— 自建最小原语 vs Radix + 自写样式为主。M1 第一周决定，不影响架构。

## Distribution Plan

- **v1（M1.5）只发 Windows**：NSIS 安装包 + portable zip。不发 `.dmg` / `.deb`，因为那两个平台上还没有可用的系统代理实现，发出去是误导。
- **Windows 未签名的代价（必须写进 README）**：没有签名时，每次下载都会触发 SmartScreen 的「未知发布者」警告；代理内核二进制也常被杀软误判（尤其国产杀软）。v1 明确接受这个代价，README 要解释「为什么会出现警告、如何继续安装」；如果采纳率明显受影响，再评估 OV 证书或云签名服务（可用性与成本需先核实）。
- **M3 起**按平台补齐：macOS（未公证，README 说明绕过隔离属性）、Linux（AppImage + .deb）。
- **M4 起**发布 Android APK（arm64-v8a 优先）。
- **GitHub Actions**：Windows job 在 M1.5 引入；矩阵构建在 M3 引入（`windows-latest` / `macos-14` 双架构 / `ubuntu-22.04`）。
- **不自动更新**。升级靠手动下载覆盖。
- **发布清单必含**：`LICENSE`（MIT）、`THIRD_PARTY_NOTICES.md`（mihomo GPL-3.0 + 源码地址）、README（**v1 只放 Windows 截图**；三平台截图在 M3 渲染验证通过后再补、已知问题：无 TUN、无 iOS、macOS 未签名、不支持订阅）。

## What I noticed about how you think

- 让你在四个产品形态里选一个，你跳出了这个题：**「现代化桌面控制台, 移动优先的极简体验, 两端共用设计规范，但不强行共用同一套页面布局」**。这句话把设计系统和页面布局拆成两件事，是这套方案里最值钱的一个判断。
