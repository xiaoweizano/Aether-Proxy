# 设计变更：托盘常驻内存预算改为 280 MB

生成于 2026-10-29
Supersedes: `docs/design/2026-10-23-aether-proxy.md` 「验收标准 → 测量协议 → 内存 → 托盘态」一项（原值 < 150 MB，更早的口径是 60–100 MB，见 `CLAUDE.md` 工程约定）
状态：APPROVED（2026-10-29 由作者在「改预算 / 做优化 / 换框架」三个方向中选定「改预算」）

## 为什么改

预算是在**还没有任何一次 Electron 实测**时定下的。M1 打包完成后第一次用真实打包产物测量，结论是目标定错了对象：不是应用写得胖，是 Electron 45 的固定成本本身就超过预算。

测量方法沿用原协议：`scripts/measure-memory.mjs`，统计 `Aether.exe` 全部进程 + `mihomo.exe` 的 Working Set（任务管理器同一列），打包版、隔离 `--user-data-dir`、关窗后只剩托盘、预热 90 秒。

| 进程 | 托盘稳态 |
|---|---|
| 主进程 | 106.8 MB |
| GPU 进程 | 84.5 MB |
| 网络服务 utility | 50.0 MB |
| mihomo | 26.8 MB |
| **合计** | **268.2 MB / 150 MB** |

三次独立运行：273.8 / 268.7 / 268.2 MB，差异来自渲染进程销毁时机与采样时点。渲染进程已随窗口销毁——这些成本与开不开窗无关。

关键事实：**GPU 进程 + 网络服务 = 134.3 MB，已经吃掉 150 MB 预算的九成**，此时应用还没画任何东西。原值 60–100 MB 在这个技术栈上不是「努力一下能到」，而是不可能。

## 为什么不选优化或换框架

- **优化**：可动的只有禁用硬件加速、精简主进程依赖、延迟初始化，乐观估计 200 MB 上下；代价是渲染手感——而手感正是这个项目选的差异点。花一轮时间换一个仍然达不到的目标，不划算。
- **换框架**：已被「三端渲染必须一致」的锁定决策排除（Tauri / Wails / Neutralino 都用系统 WebView）。

## 改了什么

| 维度 | 原设计 | 现设计 |
|---|---|---|
| 托盘态目标 | < 150 MB（此前口径 60–100 MB） | **≤ 280 MB** |
| 测量闸门 | 150 MB（`MEMORY_BUDGET_MB`） | **300 MB** |
| 超标的含义 | 常态 | **回归信号**：现行基线 268 MB，超过 300 MB 只可能是新增了不该常驻的东西 |

闸门（300）刻意高于目标（280）：三次实测跨度 268–274 MB，GPU 进程会随系统状态浮动十几 MB；闸门贴着目标就会变成随机失败，闸门的价值是抓回归，不是卡噪声。

## 什么没变

- 测量协议本身：只测打包版、Working Set 之和、关窗托盘稳态、隔离 userData。
- 开窗态预算 < 450 MB 不变。
- 「窗口隐藏即销毁（`win.destroy()`）」不变——托盘态里本来就没有渲染进程，这正是它该有的样子。
- 内存仍然是验收项：`npm run measure:memory` 退出码 1 代表超出闸门，2 代表没测到，两者都不算通过。

## 回退条件

- 若将来超出 300 MB：先按回归处理（查新增的常驻对象、依赖或定时器），不要顺手抬预算。
- 若将来真的换了桌面壳（脱离 Electron 的自绘方案）：本预算作废，按新壳的基线重新测、重新定。
